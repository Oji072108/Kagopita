# セキュリティと管理運用

## 所有者専用の管理画面

- `/admin` はログイン画面のみを公開し、機密データは返さない。
- `KAGOPITA_ADMIN_USER_ID` と `KAGOPITA_ADMIN_EMAIL` の両方を確認し、メール確認済みの本人だけ許可する。リストの `admin` / `owner` ロールとは独立している。
- 通常のアカウント認証後にパスワードを再確認し、15分の管理セッションを発行する。管理トークンは元のログインセッションに結び付け、Cookie は HttpOnly / SameSite=Strict / HTTPS時Secure。
- 管理APIは `no-store`。状態変更には同一オリジンと専用ヘッダーが必要。パスワードやトークンはログへ記録しない。
- 設定は無視対象の `.env` または実行環境へ保存する。所有者を未設定のまま公開しても誰にも管理権限を付与しない。

## 動画の公開前チェックリスト

1. APIごとにセッションとリスト参加・編集権限を検証し、他人のID指定による読み書きを拒否する。
2. パスワードはランダムソルト付きscryptで保存する。再設定トークンはハッシュで保存、30分で失効、1回使用後に無効化。変更時は以前のセッションを取り消す。
3. SQLはバインドパラメーターを使い、ユーザー文字列はテキストノードとして描画する。HTMLを許可する「サニタイズ」で表示名を改変しない。
4. APIのOriginを許可済みサイトと比較し、外部Origin / cross-siteリクエストを拒否する。CORSを認証の代わりに使わない。
5. 一般操作、チェック連打、メール、ログイン、管理再認証に独立したレート制限を適用する。
6. APIエラーは一般的なメッセージのみを返し、HTML向け404/500ページを用意する。機密ファイルとデータディレクトリは公開ディレクトリ外に置く。
7. セッション、参加者、商品、削除期限、通知等の検索条件にインデックスを用意し、`EXPLAIN QUERY PLAN` と代表的データで確認する。
8. `npm audit --omit=dev` とGit履歴の秘密情報検査を実施する。依存更新は互換性のある範囲で行い、未使用のものだけ削除する。
9. 本番は `NODE_ENV=production` と `BIND_HOST=127.0.0.1` を使用し、TLSリバースプロキシ経由で公開する。起動ログへ初期招待コードを出さない。SQLiteファイルは0600、保存先は0700。

## 監視と通知

- 管理画面はSSEで更新する。通常ユーザーの買い物画面にポーリングを追加しない。
- DB応答、空きディスク、ヒープ、イベントループ、API 5xx、ログイン成否を監視する。
- DB障害、100MB/2%未満の空き容量、継続した高ヒープ、1分に5件以上の5xxで所有者へメールと登録済み端末の高優先度プッシュを送る。同じ障害の再通知は10分抑制する。
- `/healthz` は `ok` / `critical` のみ返す。独立したスケジューラーが1分間隔で確認し、連続失敗と復旧を判定する。チェック用スクリプトは `scripts/admin-watchdog.cjs`。
- 同じホスト上の監視はアプリ停止を検出できるが、ホスト全体の停止は検出できない。完全なホスト障害には別ホストの監視が必要。

## Blue/Greenとロールバック

- 新しいリリースは別ディレクトリ・別ポートで起動し、ヘルスチェック成功後にNginxの転送先だけを切り替える。
- 切替スクリプトは `scripts/release-control.cjs`。設定ファイルのパスを `KAGOPITA_RELEASE_CONFIG` に指定する。固定された2スロット以外のコマンドやパスは管理画面から実行させない。
- `node scripts/release-control.cjs green` で切替、`node scripts/release-control.cjs rollback` で直前のスロットへ戻す。Nginx検証/リロード失敗時は以前の設定を復元する。
- SQLiteは両リリースで同じ絶対パスを参照する。移行は後方互換に保ち、切替前にオンラインバックアップとソース保存を行う。通常のコードロールバックでDBを古いバックアップに戻してはいけない。
- スロット切替前のヘルス失敗は既存トラフィックに影響させない。切替後は以前のワーカーを停止し、二重配信を避ける。

## 検証

`scripts/test-admin*.cjs`、`scripts/test-security*.cjs` と既存回帰テストを隔離DB・メールスタブで実行する。第三者/未確認メール/通常のリスト管理者/期限切れ/別セッション/CSRFを明示的に拒否し、通知の宛先・重複抑制・失敗時の動作を検証する。
